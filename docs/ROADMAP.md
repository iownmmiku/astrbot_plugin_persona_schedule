## INC-01 突发情况

### 默认配置与概率含义

| 项目 | 默认值 | 规则 |
| --- | --- | --- |
| 启用突发情况 | 关闭 | 同时受插件总开关控制 |
| 触发概率 | 0.2 | 后端接受有限数值 0～1；WebUI 显示为可调的 0～100% |
| 抽签频率 | 每个人设当地日期一次 | 按人设身份和当地日期持久化结果，多会话共享 |
| 每日次数上限 | 1 次 | 重启、刷新、日程重建、快照恢复和重新开启开关都不增加当日抽签次数 |
| 持续时间 | 15～60 分钟 | 根据事件决定，并限制在当前可调整时段内，最晚到角色当地午夜结束 |

0.2 表示具备可用时段时，当天有 20% 的抽中机会。实际生效还需要模型生成成功和触发时日程仍适用；概率为 1 也必须保护锁定安排。没有合适时段就跳过。避免按轮询、消息或每个会话反复抽签；如果每天有六个时段且每段都抽 20%，当天至少一次的概率会变成约 73.8%。

当日已经抽签后修改概率，从下一个当地日期生效；尚未抽签时使用最新配置。结果记录使用当次概率，便于解释。变更人设、时区或日程期间的旧任务必须重新核对归属与适用日期，不能使用旧计划强行触发。

### 运行流程

1. 仅处理已具备当天有效日程的角色。首次启用从当天剩余时间中查找未锁定、可调整的空闲或半忙时段，不回填已经过去的事件，也不为抽签批量生成陌生人设。
2. 完成并保存当天抽签结果。命中后，在合适的未来时间点安排一次触发机会；尚未发生的事件不进入聊天背景和当天回忆。
3. 到达触发点，使用日程生成模型，结合人设、世界观、当天活动和当前安排生成一项临时事件。共享事件生成不读取私人聊天；用户事情的重要程度仍由现有会话内弹性判断处理。
4. 校验事件是否符合身份、持续时间、回复状态和时段边界。模型返回后复核开关、人设、日期和日程版本；校验通过再保存并生效。期间已无合适时间则跳过，不追溯修改过去。
5. 生效期间统一使用变更后的实际日程。结束时恢复该时刻原本应执行的安排，并保留实际发生时间、状态和结束原因。

例：原计划为 14:00～16:00 休息，14:20 临时需要帮朋友处理事情，14:20～14:50 变为忙碌；14:50 恢复休息。研究员、店员、旅人及虚构角色分别生成符合身份的插曲，不统一套用学生生活。

首版将影响限定为一个可调整时段中的局部插入。睡眠、锁定活动及考试、值班等固定职责受到保护；连续多事件、跨日连锁重排和长期人物关系模拟不纳入首版。

### 与现有功能协作

| 功能 | 预期行为 |
| --- | --- |
| 普通回复 | 临时 busy 时静默暂存，slow 时延迟合并；结束后根据有效日程决定补回时机，并可自然提到刚才的事情 |
| 命令与范围 | 继续绕过 AstrBot 及注册插件命令；空白名单不影响全部聊天；共享事件不扩大任何会话权限 |
| 弹性联系 | 新事件使不再适用的旧联系窗口失效；需要时按当前事件重新判断用户事情的重要程度，沿用有限时长和固定职责限制 |
| 提前告知 | 不提前描述尚未发生的随机事件；事件开始后无法联系时保持静默，可在恢复后的回复中解释；不会向全部会话广播 |
| WebUI | 在时间线上显示突发标记、当前状态、原因、起止时间和原安排；允许提前结束，并保留历史 |
| 情景预演 | 支持只读模拟突发，查看前后回复状态；不消耗实际抽签、不改变真实事件或消息队列，模型模拟须显式触发 |
| 编辑与撤销 | 手工修改优先，取消冲突的待触发任务或当前事件后续影响；编辑快照不回退抽签记录，也不抹掉已发生历史 |
| 日记 | 依据真实生效的临时安排与白名单素材；未触发、跳过和模拟事件不写成已经发生的经历 |
| 随想画卷 | 联动开启时使用同一份实际安排和上下文版本；变为忙碌后取消旧主动内容，保持现有联动开关的含义 |

### 持久化与异常处理

- 保存未命中、待触发、生成中、生效中、已结束、已取消、已跳过等状态；同一角色当天只允许一个任务占用触发机会。生成失败记录原因并跳过当天机会，格式修复沿用既有有限重试规则。
- 未命中或没有候选时间时不调用事件模型；命中最多生成一项，不能因轮询、重复请求或重启反复生成。
- 关闭功能或插件时取消后续任务，结束当前事件的后续影响，保留截至关闭时已发生的历史。重新开启不重抽已处理的当地日期。
- 重启后恢复仍适用且未结束的已保存事件；已经错过的待触发任务跳过，中断的生成任务不假装成功，也不持续占用生成状态。
- 保存失败回滚内存；模型错误、过期结果或不合规事件都保留原有日程与聊天行为。

### 实现重点

以基础日程和独立事件记录计算统一的有效日程，使消息拦截、补回、弹性判断、预告、预演、日记、诊断及画卷读取一致的状态。抽签和已发生事件历史独立于可撤销的编辑快照。

现有 [main.py](../main.py) 的 `_deliver` 会检查日程对象身份；引入计算后的有效日程时，需要改为稳定的来源版本或内容指纹比较，防止每次生成新对象导致补回无限延期。[interaction.py](../interaction.py) 的联系调整来源指纹、预告边界与画卷上下文标识也要包含事件变化。异步任务提交前复核当前版本，避免把旧模型输出应用到新安排。

事件任务采用短锁记录和提交，模型调用放在锁外；统一人设锁和模型名额的获取顺序，事件生成不能在持有模型名额时反向等待被日程生成占用的人设锁。不要把这项功能仅实现为消息拦截处的一次随机判断。

## 新增优化建议的依据与验收方向

### OPT-01 多页面保存冲突检测

目前 [main.py](../main.py) 的 `web_save`、`web_save_recurrences` 和 [workbench.py](../workbench.py) 的恢复流程有锁内身份校验，但客户端不提交读取时的内容版本。[app.js](../pages/schedule/app.js) 的编辑锁主要保护当前页面。两个页面按先后顺序保存同一人设时，较旧页面仍可能提交完整旧内容。

建议读取时返回人设身份和记录版本，保存、规则更新、恢复时提交预期版本；不匹配则保留草稿、显示差异并提供重新加载入口。校验限定在人设和相关日程资料，不把新增聊天素材、日志或队列变化当作编辑冲突。不要无提示自动合并有时间重叠的日程。突发功能会增加后台变化，因此这项尤其值得优先处理。

### OPT-02 模型任务优先级与调用预算

目前日程、日记、弹性判断和留言补回共享 [main.py](../main.py) 中的三个模型名额，尚未按用途区分等待优先级；[generator.py](../generator.py) 未保存按用途的调用统计。

建议增加排队优先级或预留名额，让留言补回和即时判断优先；后台日记、预生成、突发事件公平等待，避免长期饥饿。限制主要针对可选后台任务，达到预算时采用已有安排并说明跳过原因，不用预算关闭基础聊天。提供调用次数、成功/失败和耗时；只有模型实际返回 token 用量时才显示用量，不凭空估算账单金额。进行多角色同一时刻启动的等待时间测试后再定默认值。

### OPT-03 独立备份与恢复预览

[core.py](../core.py) 的 `Store.save` 已使用临时文件替换，编辑快照与主状态仍存于同一个文件。误删或损坏主文件时，内部编辑快照无法作为独立副本恢复。

建议有限轮换本地备份，带格式版本与完整性校验；恢复前显示将变化的角色、日期和规则，并支持只恢复指定角色资料。用户可分享的导出默认仅含选定的日程资料，排除密钥、聊天原文和会话标识；完整私有备份与分享导出明确区分。恢复不重放发送队列，也不恢复已消耗的突发抽签机会。覆盖损坏文件、旧版迁移与中断恢复测试。

### OPT-04 突发事件诊断与重复抑制

建议页面提供当天状态与跳过原因：功能关闭、未命中、没有可调整时段、等待触发、生成失败、被手工修改取消等。显示“抽中概率”和“实际发生次数”的区别，避免把 20% 理解为每五天必定发生一次。

事件生成可参考同一角色近期少量事件的类型和摘要，降低连续重复；不引入其他会话的私人内容。按人设限制事件类型，角色偏好及类型权重可在后续版本再开放，不增加首版必填配置。

### OPT-05 日记归档缓冲与来源更新提示

目前 `_schedule_diaries` 在当地日期结束后为未归档日期生成一次，已存在日记不会自动重写；采集按真实收到或生成时间归属日期。归档后编辑历史日程或收到迟入库的当日素材，页面尚无统一的来源更新提示。

建议增加可配置的短暂归档缓冲，记录归档时的日程版本与素材采集位置，用于提示“依据已更新，可重写”。只在日程变化或新增素材时提醒，聊天素材自然过期或被清理不应导致反复提示和重写。用户选择重写时再调用模型，保持已归档内容稳定。午夜后的回复仍归次日，不能为了配对强行挪到前一天；未收到或未知的回复不编造。先用历史日程编辑、跨午夜与慢环境查询案例明确边界，再定缓冲时长。

### OPT-06 状态存储性能测量

目前消息素材、队列及部分任务状态变更会同步重写整个 JSON 状态。文件较大或磁盘较慢时，可能增加事件循环等待；当前没有性能基准，不能直接判定已造成卡顿。

建议先测量状态文件大小、单次写入耗时和消息处理延迟，再评估分离日记归档或合并非关键写入。发送前状态、白名单撤销、事件触发记录等可靠性关键写入仍须及时落盘。存储迁移必须具备备份、回滚和旧版本数据验证，不为未测量的收益立即引入数据库依赖。
